# EVM Inventory and Bitget Consolidation

CLI для инвентаризации EVM-кошельков, подготовки маршрутов к депозиту на Bitget и их явного выполнения. Все рабочие команды используют один локальный SQLite-файл через `--db`. Подпись и отправка транзакций возможны исключительно с флагом `--execute`.

`--execute` разрешает перемещение средств. `collect-wallet` автоматически выполняет полный цикл; отдельные команды сканирования, планирования и выполнения доступны для диагностики.

## Установка и доступы

```bash
uv sync
cp .env.example .env
```

В `.env` указываются только нужные конкретному режиму ключи:

| Переменная | Для чего нужна |
| --- | --- |
| `ALCHEMY_API_KEY` | Более полное обнаружение ERC-20 при сканировании (необязательно). |
| `ALCHEMY_RPC_API_KEY` или `ALCHEMY_API_KEY` | RPC для отправки транзакций при выполнении. |
| `BITGET_API_KEY`, `BITGET_SECRET_KEY`, `BITGET_PASSPHRASE` | Получение живого каталога депозитов и выполнение маршрутов. |
| `LIFI_API_KEY` | Авторизованная квота LI.FI. Без ключа действует ограничение бесплатного доступа; программа ждёт его сброса. |
| `RELAY_API_KEY` | Ключ для запросов Relay, если провайдер требует авторизацию. |
| `MAX_ROUTE_LOSS_PCT` | Максимальная суммарная потеря на кошелёк и исходную сеть; по умолчанию `15`, допустимый диапазон `(0, 100]`. |

Приватные ключи берутся из workbook только на время выполнения и не записываются в отчёты, план или базу.

Все команды проекта работают в одном процессе: CLI вызывает функции напрямую и не запускает дочерние команды. После `uv sync` запускайте установленный исполняемый файл `.venv/bin/evm-inventory`; для пакетной очереди используйте `.venv/bin/python -m evm_inventory.defi_batch`. Это правило проверяется тестом исходников для `src/` и `scripts/`.

## Режимы работы

### Полный сбор одним запуском, без Rabby

```bash
.venv/bin/evm-inventory collect-wallet \
  --workbook local/wallets.xlsx \
  --wallet-ranges 3 \
  --db out/inventory.sqlite \
  --output out/wallet-3-collection \
  --execute \
  --trust-deposit-addresses
```

`--trust-deposit-addresses` нужен при первом выполнении после проверки точного адреса Bitget из workbook. Доверие сохраняется для пары кошелёк/получатель в той же SQLite; при последующих запусках флаг можно опустить. Изменение получателя требует новой проверки. Без `--execute` команда только сканирует и рассчитывает маршруты.

В одном процессе команда сканирует все настроенные сети, проверяет известные и разрешённые токены через RPC, добавляет discovery, выбирает исполнимые маршруты, выполняет их и ждёт receipt, завершения мостов и зачисления Bitget. Она повторяет временные ошибки и незавершённые направления, соблюдает `Retry-After` и продолжает pending-операции сама. Готовые группы сетей выполняются и проверяются во время ожидания остальных котировок; группа с незавершённым планированием сохраняет газ для своих ERC20. План записывается в общую SQLite до первой отправки, а позиции с отправленными транзакциями сохраняют исходный план. Неподписанные активы той же сети продолжают поиск отдельно. Отказ одного направления по минимуму не завершает поиск, если альтернативы ждут квоту или ответ провайдера; до завершения такого поиска новые переводы из этой сети сохраняют газ, а отправленные продолжают проверяться. Для нативных монет котируется доступная сумма после резерва газа; перед отправкой сумма уточняется по живому балансу и RPC-комиссии. При отсутствии ERC20 allowance планируется ограниченная комиссия, затем подтверждается `approve` и проводится фактическая симуляция маршрута перед его подписью.

Режим `best_available` последовательно проверяет настроенные направления и прекращает дополнительные запросы, когда подготовлен маршрут в пределах бюджета потерь. Пригодный прямой депозит также не требует запросов к другим направлениям. Ошибка одного направления не блокирует проверку следующего. Поиск сохраняет `search.complete=false` и причины пропущенных направлений (`alternative_destination_not_requested`); минимальная стоимость среди всех целей при этом не заявляется. Неизвестный газ, неверный актив или получатель не разрешают отправку. Временные сетевые ошибки и смена идентификатора свежей котировки обрабатываются автоматически; идентичность активов, сумма, минимальное получение Bitget и бюджет потерь проверяются перед исполнением. Relay используется как дополнительный провайдер для поддерживаемого одношагового нативного входа в EVM-сетях.

Все стадии используют одну `--db`. План сохраняется до исполнения; после прерывания запущенные переводы продолжаются по сохранённым хешам. Завершённые позиции не отправляются снова. Если незавершённый перевод уже существует, изменение его политики или получателя блокируется. Выходная папка содержит `wallet-3/inventory/`, `wallet-3/plan.json` и `result.json` с точными причинами оставшихся позиций. `denied` содержит `reason` и `reason_detail`: явный запрет отличается от отсутствия точной пары сеть/контракт в allowlist.

По умолчанию общий предел — три часа на кошелёк (`--max-runtime-seconds 10800`, максимум 86400), включая ожидание квот; часть времени оставляется для исполнения. Пределы коротких диагностических стадий не требуют перезапуска полной команды. Реальные ограничения внешних API сохраняются: [LI.FI публикует отдельные квоты для доступа с ключом и без него](https://help.li.fi/hc/en-us/articles/12111455848859-What-is-the-LI-FI-API-rate-limit). Если провайдер недоступен до конца бюджета, команда сохраняет незавершённое состояние и возвращает код 3. Отсутствие средств на газ, слишком маленькие или невыгодные позиции перечисляются в `skipped`; неизвестные токены получают объяснённый отказ allowlist. `completed_with_skips` означает завершение доступных операций с указанным остатком.

Rabby API и расширение Rabby в этом режиме не вызываются. Название колонки `Прокси Rabby` сохранено ради совместимости workbook: её прокси используют LI.FI и Relay.

### 1. Проверить входной список без сети

`scan --dry-run` валидирует файл с адресами и не делает RPC/API-запросов:

```bash
.venv/bin/evm-inventory scan \
  --wallets input/wallets.txt \
  --db out/inventory.sqlite \
  --dry-run
```

Файл содержит по одному публичному `0x`-адресу на строку.

### 2. Собрать инвентарь кошельков

Обычный `scan` читает балансы нативных монет, известных токенов и результаты discovery. Транзакции не подписываются и не отправляются.

```bash
.venv/bin/evm-inventory scan \
  --wallets input/wallets.txt \
  --db out/inventory.sqlite
```

Инвентарь, планы и состояние выполнения сохраняются в одном файле `out/inventory.sqlite`. Перед планированием убедитесь, что нужные сети и токены имеют полное покрытие: отсутствие цены, RPC-ответа или discovery не считается нулевым балансом.

Для каждого кошелька `scan` и `execute-routes` сохраняют жёсткий бюджет `--stage-seconds` (по умолчанию 30 секунд, больше 30 запрещено). Для `quote-routes` этот параметр — ориентир времени: после его превышения выводится предупреждение, но сравнение маршрутов продолжается. В отчёт записываются фактическое время и признак превышения (`quote_timing`). Таймауты отдельных HTTP-запросов, квоты API и ограничения параллелизма действуют независимо от этого ориентира. Скан читает сети параллельно: `--workers 16`; котировки обрабатывают до шестнадцати групп и позиции внутри группы параллельно: `--workers 16 --target-workers 8`. LI.FI-запросы одного кошелька проходят через общую очередь. Повторные запросы цены объединяются в пределах кошелька. Незавершённые проверки скана получают `deferred`; если сравнение котировок неполно из-за ошибок API или квот, группа получает `manual_review`. Само превышение ориентира времени не делает поиск неполным. Старый баланс не подставляется вместо свежего ответа. Повторный запуск продолжает работу с той же базой.

Для выгрузки уже собранного JSON в плоский CSV:

```bash
.venv/bin/evm-inventory export \
  --db out/inventory.sqlite \
  --output out/inventory-export
```

Ошибки скана сохраняются с диагностикой в общей SQLite-базе и выводятся в `error_details`: тип исключения, текст, попытки запроса, метод RPC, ответ провайдера и traceback. Секреты удаляются перед сохранением. `checks.csv` содержит колонку `diagnostic`, `coverage.csv` — `discovery_error`; при несовпадении адреса или сети discovery указывает конкретное поле, ожидаемое и полученное значения. Ошибки котировок и оценки газа также сохраняют полную диагностику в JSON-отчёте. Статус `provider_only` учитывается отдельно в `discovered_provider_only`: это данные провайдера без независимой проверки RPC, а не ошибка запроса.

Экспорт создаёт `balances.csv`, `checks.csv`, `coverage.csv` и `inventory.json` в `out/inventory-export`.

### 3. Подготовить и проверить workbook

Шаблон содержит адрес кошелька, приватный ключ и адрес депозита Bitget:

```bash
.venv/bin/evm-inventory workbook-template \
  --output input/wallets.xlsx
```

Проверка workbook не подписывает транзакции, но требует корректные поля у всех его строк и может записать служебные статусы в файл:

```bash
.venv/bin/evm-inventory workbook-dry-run \
  --workbook input/wallets.xlsx
```

### 4. Сделать план без отправки средств

Основной режим планирования получает живой каталог депозитов Bitget и котировки LI.FI, но остаётся read-only: кошельки не разблокируются и транзакции не создаются.

Все запросы LI.FI (цены, маршруты, подготовка транзакций и статусы) выполняются через индивидуальный прокси кошелька из колонки `Прокси Rabby` в XLSX. Прямого подключения при ошибке прокси нет. При наличии `LIFI_API_KEY` передаётся заголовок `x-lifi-api-key`, квота и очередь общие для этого ключа независимо от прокси; без ключа учёт ведётся по отпечатку прокси. До двух запросов находятся в полёте; старты HTTP разделяются минимум одной секундой общей очередью в SQLite. Совпадающие запросы объединяются.

Поиск использует до трёх конечных целей из `--route-targets` (по умолчанию `config/route-targets.json`: USDC в Base, Optimism и Arbitrum). Каждая цель проверяется по точной сети, контракту, coin и актуальным параметрам депозитов Bitget. Недоступные цели перечисляются в `search_scope.unavailable_targets`, без подмены. LI.FI получает один запрос `CHEAPEST` на направление и сам подбирает swap/bridge внутри него. Дополнительно сравниваются прямой депозит исходного актива, если он принимается Bitget, и локальный unwrap канонического WETH с последующим депозитом ETH в той же сети. Самый дешёвый вариант выбирается **среди этих активных целей**, а не среди всех депозитных активов биржи (`search_scope.global_cheapest=false`).

Сначала собираются и проверяются все маршруты из ответов без подготовки calldata. Нижняя граница потерь считается с нулевым газом; подготовка выполняется в порядке этой границы. После уточнения стоимости победителя пропускаются только кандидаты, чья нижняя граница строго больше его стоимости. Равенство границ не отсекается. Оценка газа LI.FI не считается доказанной нижней границей.

Если хотя бы один необходимый запрос не завершён, не хватает цен или нельзя уточнить газ возможного победителя, план получает `route_search_incomplete` и `search.complete=false`. Промежуточный кандидат записывается как `provisional_candidate` и не исполняется. План сохраняет число предварительных кандидатов, подготовленных и отсечённых маршрутов, причины незавершённости и HTTP-счётчики `lifi_requests`. Сравнивается стоимость среди полученных актуальных котировок, с консервативной RPC-оценкой газа; фактически уплаченная комиссия может отличаться.

Для CELO (chain `42220`) native-баланс и баланс ERC20-контракта `0x471ece3750da237f93b8e339c536989b8978a438` — представления одних средств. Планировщик объединяет подтверждённые записи в одну контрактную позицию, сохраняет `balance_aliases` и не складывает суммы. Если суммы различаются (включая ноль), ставится `conflicting_native_balance`. Для этой позиции действует правило allowlist по контракту; по умолчанию разрешён `swap`. LI.FI получает контрактный адрес CELO также при запросе цены native-газа; цепочка, decimals и адрес ответа проверяются. ERC20 allowance маршрута остаётся обязательной проверкой.

Прямой депозит CELO удерживает газ из того же баланса. Нулевая `baseFeePerGas` в BSC/Core использует живой `eth_gasPrice`. В Scroll к газу исполнения добавляется L1-комиссия oracle по полному размеру подписанной RLP-транзакции, с запасом 20%. Неподписанные прямые депозиты получают свежую симуляцию и общий предел комиссии перед исполнением. Для сохранённых операций старого кода предусмотрены два ограниченных восстановления: окончательно откатившийся перевод полного баланса CELO повторяется после проверки причины, с учётом уже потраченного газа; отсутствующий перевод Scroll с пропущенной L1-комиссией заменяется строго с прежним nonce. Оба хеша Scroll сохраняются, проверяется фактический победитель. Nonce и хеш подписанного намерения записываются атомарно до отправки; обрыв до отправки подготовленного прямого депозита восстанавливается только идентичными подписанными байтами после проверки хеша и digest. Каждое восстановление сохраняет исходные адрес, актив, депозитный минимум и бюджет потерь, а неподписанное продолжение проверяет их снова.

Перед расчётом читается текущий список сетей LI.FI через прокси кошелька, с общим HTTP-кешем. Позиции в неподдерживаемых сетях остаются в отчёте с `unsupported_by_lifi` и `alternative_provider_required=true`; цены и маршруты LI.FI для них не запрашиваются. Недоступный или неверный каталог поддержки блокирует расчёт с `lifi_chain_catalog_unavailable`, а не обозначает сети как неподдерживаемые. Сканирование этих сетей сохраняется; другие мосты/свап-провайдеры подключаются отдельно.

Квоты, результаты поиска и HTTP-кэш хранятся в той же `--db`. Повторный запуск использует ещё актуальные результаты и запрашивает недостающие пары. Маршруты кэшируются на 240 секунд, unsigned calldata на 120 секунд, цены на 60 секунд, статусы на 10 секунд. Кэш сохраняет первоначальное время получения; чтение не продлевает актуальность. Баланс, выбранный маршрут, газ и депозитные ограничения повторно проверяются перед исполнением.

Квота учитывается по SHA-256 отпечатку ключа или прокси, без записи их учётных данных. Для доступа без ключа консервативные окна: routes/quote — 65 за два часа, stepTransaction — 40 за два часа, прочие endpoints — 80 за минуту. С ключом применяется опубликованная авторизованная квота: до 12000 запросов маршрутов/подготовки за два часа и 100 прочих запросов за минуту; меньший лимит из заголовков провайдера имеет приоритет. Планирование сохраняет резерв 5 запросов маршрутов и 3 подготовки шагов для execution-requote. При исчерпании квоты направление сохраняется с `retry_at`; `collect-wallet` ожидает продолжения внутри текущего запуска. После 429 другие процессы также соблюдают сохранённый cooldown.

Таблица `quote_jobs` в той же базе сохраняет каждую пару, исходный ответ и его возраст; ключ включает область квоты, точные токены и decimals, сумму, отправителя/получателя, slippage, политику и каталог целей. Атомарная claim/lease и сравнение владельца/попытки защищают от двойной отправки и поздних ответов. Временные транспортные ошибки и 5xx повторяются до трёх раз с паузами; полный режим продолжает незавершённые группы в пределах общего бюджета. Неизменный ошибочный запрос 4xx не отправляется повторно. Свежие ответы используются снова, устаревшие пересчитываются. HTTP-попытки, кеш, объединённые запросы, ожидания квоты и фактические 429 считаются отдельно.

Внешнее использование того же выходного IP может расходовать общую квоту и вызвать 429 независимо от локального счётчика. Ограничения снижают расход и предотвращают повторный спам; отсутствие 429 при внешнем расходе гарантировать нельзя.

```bash
.venv/bin/evm-inventory quote-routes \
  --balances out/inventory-export/balances.csv \
  --workbook input/wallets.xlsx \
  --db out/inventory.sqlite \
  --output out/routes-plan.json \
  --wallet-ranges 5 \
  --route-targets config/route-targets.json \
  --quote-floor 0.01
```

`--wallet-ranges 5` выбирает только кошелёк №5; допустимы отдельные номера и диапазоны, например `1,3-5,8`. `--quote-floor` — минимальная оценка позиции в USD для запроса котировки.

Для Zora (7777777), Shape (360) и Superseed (5330), если сеть отсутствует в каталоге LI.FI, `quote-routes` дополнительно использует Relay. В полном режиме Relay также пробуется для нативных EVM-позиций, для которых LI.FI не дал исполнимого маршрута. Запросы идут непосредственно к `api.relay.link` через прокси соответствующего кошелька; `RELAY_API_KEY` передаётся при наличии. Документация Relay требует ключ для `/quote/v2`, поэтому при отказе авторизации сохраняется конкретная ошибка 401.

Relay сравнивает три настроенные цели USDC, проверяет точные сети, адреса токенов, decimals, суммы и получателя. Для ETH резервируется 120% предварительной оценки исходного газа, затем маршруты пересчитываются на доступную сумму. Цены и комиссии берутся из ответа для проверенной пары активов. Предварительная оценка потерь включает минимальное получение и исходный газ. Получатель результата — сразу депозитный адрес Bitget из workbook. Результаты находятся в `relay_candidates`, выбранный вариант — в `relay_selected`; `relay_summary` и `relay_requests` показывают охват и расход запросов. Ответы и ошибки сохраняются в `quote_jobs` общей базы, кеш живёт 240 секунд. Квоты Relay отделены от LI.FI, локальный предел котировок — 40 в минуту, до двух запросов одновременно с интервалом начала не менее секунды; 429 сохраняет cooldown без немедленного повтора.

Relay поддерживает исполнение одношагового `depositNative` для нативных монет с 18 decimals в EVM-сетях, подтверждённых живыми RPC и каталогом `/chains`, с получением USDC прямо на доверенный адрес Bitget. Без `--execute` и подтверждения доверия адресам отправка блокируется. Перед подписью исполнитель получает свежую котировку без кеша, проверяет живой баланс, актуальный минимум Bitget, максимальную комиссию RPC и потери (не выше 15%; увеличить этот предел для Relay нельзя). Расчёт заказа повторяет EIP-712 схему официального settlement SDK 0.0.146: проверяются order ID, канонический контракт из `/chains`, точные calldata, вход, выход, получатель и срок заказа. Подписи сообщений, произвольные вызовы, ERC20-вход и многошаговые маршруты не исполняются.

Хеш исходной транзакции сохраняется в общей `--db` до отправки. Повторный запуск наблюдает сохранённый перевод, не подписывает его заново. Проверяются исходный receipt, статус `/intents/status/v3`, хеши и сети, USDC Transfer в receipt назначения и зачисление Bitget. Незавершённый перевод остаётся pending; ошибки сохраняются в `relay_diagnostic` общей таблицы `route_checkpoints`. Refund/failure не вызывают повторной отправки. Доступ к подготовке Relay сериализован файловым lock рядом с общей базой. Реальная отправка в рамках внедрения не выполнялась. Превышение потерь и незавершённое сравнение остаются отдельными блокирующими причинами. Ключи MoonPay из фронтенда для Relay не используются.

Также доступен упрощённый офлайн-классификатор без Bitget и LI.FI. Он не даёт исполнимых котировок — для реального маршрута используйте `quote-routes`:

```bash
.venv/bin/evm-inventory route-plan \
  --balances out/inventory-export/balances.csv \
  --db out/inventory.sqlite \
  --output out/offline-plan.json \
  --quote-floor-raw 100
```

#### Правила планировщика

- Депозит допускается только при точном совпадении `chain_id` и идентификатора актива с живой сетью и монетой Bitget.
- Адрес получателя берётся из workbook и считается указанным оператором адресом Bitget. У публичного API Bitget нет метода получения полного списка дополнительных депозитных адресов основного аккаунта и субаккаунтов; методы `deposit-address` возвращают один адрес. Код не проверяет принадлежность получателя Bitget. За правильность адресов и выбранных сетей отвечает тот, кто заполнил таблицу.
- Все непустые депозитные адреса во всей таблице должны быть уникальны, включая строки вне `--wallet-ranges`. При сравнении игнорируются регистр и пробелы по краям. Дубликаты останавливают планирование и выполнение с указанием адреса и номеров строк Excel.
- USD-стоимость используется только при полной свежей оценке. Неполные, отсутствующие или некорректные цены переводят позицию в ручную проверку.
- Для Ethereum native ETH и канонического WETH (`0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2`) цена LI.FI проверяется по точному контракту WETH через DeFiLlama. При расхождении более 20% используется цена DeFiLlama с давностью не более пяти минут и confidence не ниже 0,90. Недоступная или некорректная проверочная цена блокирует оценку. План сохраняет использованную цену, её источник, исходную цену LI.FI, оценку баланса и порог `dust`.
- Комиссии LI.FI учитываются по иерархии: агрегат родительского шага используется один раз, без повторного добавления вложенных расходов. При отсутствии агрегата используются расходы дочерних шагов. Если агрегат не покрывает вложенные расходы по точному активу и raw-сумме, маршрут остаётся на ручной проверке; сводные поля комиссий в корне маршрута не обязательны.
- Планировщик рассматривает живые котировки LI.FI для включённых целей Bitget и проверяет точные идентификаторы исходного и целевого активов, сумму, получателя и структуру исполняемых шагов.
- Для каждого кошелька и исходной сети планировщик выбирает маршрут с наименьшей оценённой потерей; сумма потерь и оплачиваемого кошельком газа ограничена `MAX_ROUTE_LOSS_PCT` от стоимости исполнимых балансов этой группы.
- Балансы с действиями `deny` или `review`, пылевые суммы и строки без адреса депозита не увеличивают знаменатель группы и не допускаются к отправке.
- Допустимое направление и провайдер заранее не задаются в конфигурации: LI.FI-котировка принимается только после структурной проверки маршрута и точного совпадения идентичности активов.
- Если свежая проверка маршрута, цены, газа, целевого минимума Bitget или бюджета группы не проходит, позиция получает `manual_review`, а оставшиеся отправки этой группы останавливаются.
- Для последовательности `swap_to_native → bridge` исполнитель измеряет фактический результат swap, повторно котирует bridge с фактического native-баланса и сохраняет старый и новый маршрут в общей базе. Неоднозначный результат отправки не приводит к слепому повтору транзакции.
- Если перед финальным шагом нужен переход в другую сеть, исполнитель опрашивает LI.FI `/status` до подтверждённого прихода, сверяет получателя, токен и фактический баланс, затем повторно котирует оставшийся путь. Перед следующей подписью он заново проверяет цену, газ, минимум Bitget и общий лимит потерь группы; статус `PENDING` обрабатывается автоматически.

Список `assets` в `config/swap-allowlist.json` по-прежнему задаёт действия для точных пар `chain_id` и `asset_id`; одного символа для допуска актива недостаточно.

### 5. Выполнить утверждённый план

**ОБЯЗАТЕЛЬНО ПРОВЕРЬТЕ ЧТО ЗА АДРЕСА ДЕПОЗИТОВ ВЫ ТУДА ВСТАВИЛИ.** Программа доверяет таблице. Без явного подтверждения `--trust-deposit-addresses` выполнение блокируется с этим предупреждением до чтения плана и изменения базы. Убедитесь, что каждый адрес действительно принадлежит нужному аккаунту Bitget и подходит для выбранного актива и сети. Флаг означает, что вы проверили адреса и принимаете ответственность за них; предупреждение сохраняется и при запуске с флагом.

Проверьте JSON плана и депозитные адреса, затем запустите выполнение с обязательными `--execute` и `--trust-deposit-addresses`:

```bash
.venv/bin/evm-inventory execute-routes \
  --plan out/routes-plan.json \
  --workbook input/wallets.xlsx \
  --catalog src/evm_inventory/data/catalog.json \
  --db out/inventory.sqlite \
  --wallet-ranges 5 \
  --execute \
  --trust-deposit-addresses
```

Если повторение депозитных адресов намеренное, добавьте `--allow-duplicate-deposit-addresses`. Этот флаг доступен у `workbook-dry-run`, `quote-routes` и `execute-routes`; его нужно передать каждой запускаемой команде. Он отключает только проверку уникальности. При выполнении с флагом программа дополнительно предупреждает, что проверка уникальности отключена.

Исполнитель хранит намерение, nonce и хеш транзакции в той же базе до и после broadcast. При неоднозначном RPC-ответе он восстанавливает состояние по nonce/хешу вместо слепой повторной отправки. Причина ошибки сохраняется там же рядом со статусом маршрута.
После отправки исполнитель проверяет receipt и состояние депозита Bitget без длительного ожидания. Незавершённая транзакция, bridge или депозит сохраняются в общей базе как ожидающие продолжения. Повторите `execute-routes` с тем же планом, `--db`, `--execute` и `--trust-deposit-addresses`: исполнитель сначала проверит сохранённый хеш без новой подписи, затем продолжит маршрут с сохранённого шага. Сохраняются также исходные балансы swap и фактические результаты промежуточных шагов. Перед следующей подписью обязательны свежие проверки цены, газа и лимитов. Новый план с тем же кошельком, сетью и активом не отправляется, пока прежний депозит не закрыт. Подтверждение блокчейна и зачисление Bitget могут занять больше 30 секунд; команда возвращает управление с сохранённым состоянием. По умолчанию паузы между кошельками отсутствуют; явно заданные в плане задержки сохраняются.

Для Ethereum Mainnet верхняя цена газа EIP-1559 рассчитывается как `ceil(baseFee × 1.3)` и по-прежнему проверяется против настроенного лимита.

### 6. Посмотреть состояние выполнения и восстановить контекст

```bash
.venv/bin/evm-inventory resume-routes \
  --db out/inventory.sqlite
```

Команда только читает общую базу и выводит счётчики групп, позиций и транзакционных шагов, а также причины ручной проверки. Она не загружает workbook или ключи, не делает RPC-запросов, не меняет базу и не отправляет повторные транзакции. Это первый шаг после прерывания или ошибки выполнения; состояния `source_asset_converted_bridge_pending`, `requote_required` и `manual_review_after_swap` требуют ручного разбора.

### Сквозной запуск

```bash
.venv/bin/evm-inventory scan --wallets input/wallets.txt --db out/inventory.sqlite
.venv/bin/evm-inventory export --db out/inventory.sqlite --output out/inventory-export

Проверьте JSON-план: конкретную сеть и актив Bitget, адрес получателя, сумму, шаги и групповой `loss_pct`. Затем выполните выбранные диапазоны только с явным `--execute` и после завершения или прерывания прочитайте состояние общей базы:

  --workbook input/wallets.xlsx --catalog src/evm_inventory/data/catalog.json \

.venv/bin/evm-inventory resume-routes --db out/inventory.sqlite
```

## Вывод средств из DeFi через действия Rabby

Rabby возвращает для части DeFi-позиций готовые `withdraw_actions`. Для каждого кошелька заполните колонку `Прокси Rabby` в XLSX: URL вида `http://user:pass@host:port`, `https://user:pass@host:port` или `socks5://user:pass@host:port`. Команды `quote-defi` и `execute-defi` обращаются к Rabby только через прокси соответствующего кошелька; при пустом или неверном прокси команда останавливается. Прокси и приватные ключи не записываются в план или базу. Поддерживаются простые прямые выводы; позиции с долгом, proxy-контрактом, очередью вывода, неоднозначным действием или неподдержанной функцией получают `manual_review`.

При ответе Rabby HTTP 429 каждый GET повторяется ещё три раза с экспоненциальными паузами 5, 10 и 20 секунд. Если сервер прислал `Retry-After`, он задаёт нижнюю границу первой паузы; следующие паузы удваиваются. После исчерпания попыток действие передаётся на `manual_review`, а не в `skipped`; ошибка 429 при построении плана переносит весь кошелёк на повторную попытку. Ответы 429 и сроки повторов записываются в лог.

```bash
.venv/bin/evm-inventory quote-defi \
  --wallets input/wallets.txt \
  --workbook input/wallets.xlsx \
  --db out/inventory.sqlite \
  --output out/defi-plan.json
```

Команда выводит `plan_sha256`. В `defi-plan.json` найдите нужную строку со статусом `ready`, проверьте сеть, протокол, адрес контракта, `func`, `str_params`, получателя и при необходимости `need_approve`. Скопируйте её `action_id`. План действует 15 минут. Выполняется **ровно одно** выбранное действие:

```bash
.venv/bin/evm-inventory execute-defi \
  --plan out/defi-plan.json \
  --plan-sha256 <plan_sha256> \
  --action-id <action_id> \
  --workbook input/wallets.xlsx \
  --db out/inventory.sqlite \
  --max-gas-wei 1000000000000000
```

Без `--execute` команда только обновляет данные Rabby, проверяет RPC и показывает необходимый газ. Если для действия нужна новая транзакция `approve`, выполнение останавливается с сообщением о необходимости отдельного разрешения. Для подписи и отправки подготовленного вывода повторите проверенную команду с `--execute`.

Все позиции, действия и результаты Rabby сохраняются в той же базе (`--db`), что и инвентарь, планы маршрутов и состояние их выполнения. JSON остаётся файлом для просмотра и подтверждения SHA-256. Намерение отправки, nonce и хеш транзакции также находятся в этой базе для восстановления после сбоя. Существующая база инвентаря версии 2 или 3 автоматически обновляется до версии 4 при записи.

Перед подписью действие заново сверяется с Rabby, проверяются контракт, получатель, allowance, сеть и лимит газа. После подтверждения `removeLiquidity` результат `withdrawn` выдаётся только тогда, когда логи самой транзакции подтверждают получение обоих токенов не меньше указанных в действии минимумов. Для блокировки veSTG на BNB Chain дополнительно сверяются события `Withdraw` и перевод STG на тот же кошелёк с точно совпадающей суммой. Для остальных методов подтверждённая транзакция получает `manual_review`: Rabby не всегда сообщает точный выходной актив и минимальный результат. Повторный запуск с тем же `--db` наблюдает уже отправленную транзакцию и не подписывает новую. Комиссия Rabby за сам вызов вывода в опубликованном коде не указана; возможны газ и комиссии самого протокола.

После вывода запустите обычный `scan` и `quote-routes`, чтобы обработать полученные на кошелёк токены.

Для пакетного вывода из уже сохранённого в общей базе плана используйте `python -m evm_inventory.defi_batch init`, затем `run` с тем же `--db` и `--run-id`. При `init` можно задать два независимых интервала в секундах:

```bash
.venv/bin/python -m evm_inventory.defi_batch init \
  --db out/inventory.sqlite --workbook local/wallets.xlsx \
  --seed-plan out/defi-plan-1-50.json --run-id defi-first-50 \
  --output-dir out/defi-batch-first-50 \
  --between-wallet-delay-min-seconds 1200 \
  --between-wallet-delay-max-seconds 6000 \
  --within-wallet-delay-min-seconds 60 \
  --within-wallet-delay-max-seconds 300
.venv/bin/python -m evm_inventory.defi_batch run \
  --db out/inventory.sqlite --run-id defi-first-50
```

По умолчанию задержка между транзакциями разных кошельков составляет 20–100 минут, а между транзакциями одного кошелька — 1–5 минут. Пауза проверяется перед новой отправкой; запросы к Rabby и RPC для просмотра и оценки газа её не расходуют. Параметры запуска и сроки хранятся в общей SQLite-базе, поэтому после перезапуска очередь продолжает работать с теми же настройками.

## Что проверять перед боевым прогоном

1. Инвентарь покрывает все нужные сети и токены, а проблемные строки разобраны.
2. В `routes-plan.json` нет `manual_review`, `unknown` или неподтверждённых действий.
3. Сумма, комиссия, газовый резерв, сеть назначения и адрес депозита экономически приемлемы для каждого маршрута.
4. Для каждого маршрута проверьте точную цель Bitget, получателя, идентичности активов и структурные данные котировки LI.FI.
5. Общая база сохранена в устойчивом месте и перед повторным запуском проверена через `resume-routes`.

## Безопасность

Не добавляйте `.env`, workbook с приватными ключами, планы с чувствительными данными и локальную базу в Git. Используйте отдельный тестовый кошелёк перед первым боевым запуском и ограничивайте `--wallet-ranges`, пока не убедитесь в поведении на одном кошельке.

Из сканирования, экспортов текущих балансов, планирования и выполнения исключены Ethernity (183), Mint (185), Binary (624), Redstone (690), RACE (6805), Polynomial (8008), Automata (65536), Silent Data (380929), Xterio Chain ETH (2702128). Исключение действует также для пользовательских каталогов и ранее сохранённых планов; исторические записи общей базы сохраняются. Список задан в `src/evm_inventory/network_policy.py`.
